# AI Code Wisdom 実装仕様 v0.1（MVP）

> 全体の設計は `AI-Code-Wisdom-設計書.md` を参照。この文書は実装する人向けの契約（関数の形・出力・挙動）。

## 0. 共通の約束

- Node 26 で `.ts` を**ビルドせず直接実行**する（型の除去のみ）。enum・namespace・constructor の引数プロパティなど、型以外の構文は使わない（`tsconfig.json` の `erasableSyntaxOnly`）。import は `./x.ts` のように拡張子付き。型だけの import は `import type`。
- 依存は `yaml` と `@ast-grep/cli` だけ。新しい依存を足さない。
- 利用者に見える文言は日本語。コメントは既存の `src/core/*.ts` と同じく、要点だけ短く。
- ライセンス欄（package.json の license、LICENSE ファイル、README の License 節、plugin.json の license）は、**本人が指定したライセンスだけ**を書く。実装する側から提案したり変えたりしない。
- フックは**絶対に利用者のセッションを壊さない**：例外はすべて捕まえ、`.wisdom/cache/hook-errors.log` に追記して、何も出力せず終了コード 0 で終わる。ただし設定を読めない（`loadCompiled` が失敗した）ときは、検査が黙って止まらないよう、session-start でだけ additionalContext に「自動検査が止まっていること・理由（例外のメッセージ）・`wisdom status` で確かめること」を出す（終了コードは 0 のまま。ほかのフックは何も出さない）。
- 型チェック `npx tsc -p tsconfig.json`、テスト `npm test`（`node --test "test/**/*.test.ts"`）が通ること。

## 2. `src/core/checker.ts`

```ts
export interface Finding {
  ruleId: string;        // .tsx 用の複製の接尾辞 "__tsx" は取り除く
  principle: string;
  severity: Severity;
  blocking: boolean;     // ActiveRule.blocking
  file: string;          // プロジェクトルートからの相対パス（区切りは /）
  line: number;          // 1 始まり
  endLine: number;       // 1 始まり
  column: number;        // 1 始まり
  message: string;
  note?: string;
  snippet: string;       // 一致した部分の1行目を trim、最大 120 文字
  fingerprint: string;   // sha1(ruleId + "\0" + 一致した全文の空白を1つにまとめたもの) の先頭 12 桁
}
export interface Waiver { finding: Finding; reason: string }
export interface CheckOptions { paths?: string[]; diffBase?: string }
export interface CheckResult {
  findings: Finding[];       // 例外にしたものを除く
  waived: Waiver[];
  invalidAllows: Finding[];  // wisdom-allow はあるが理由がないもの（findings にも残す）
  filesScanned: number;
  errors: string[];
}
export function astGrepBin(): string
export function check(paths: ProjectPaths, compiled: Compiled, opts?: CheckOptions): CheckResult
export function diffFingerprints(before: string[], after: Finding[]): Finding[]
export function changedLineRanges(root: string, base: string, relFile: string): [number, number][] | "all" | null
```

- `astGrepBin()`：`PLUGIN_ROOT/node_modules/.bin/ast-grep` があればそれ、なければ PATH の `ast-grep`。
- 対象：`opts.paths` が空ならプロジェクトルート全体。指定があれば、存在しないものと、`languageOf` が null のファイルを除く。残りがなければ空の結果を返す。
- 実行：`spawnSync(bin, ["scan", "-c", compiled.sgconfig, "--json=stream", "--include-metadata", ...除外, ...対象], { cwd: root, maxBuffer: 256MB })`。除外は `--globs` に `!**/node_modules/**` `!**/.git/**` `!**/dist/**` `!**/build/**` `!**/.venv/**` `!**/venv/**` `!**/__pycache__/**` `!**/.wisdom/**` を渡す。終了コード 0 と 1 は正常（1 は error の検出あり）。それ以外は `errors` に stderr を入れる。
- 出力は1行に1つの JSON。使う項目：`ruleId`、`severity`、`message`、`note`、`file`、`range.start.line`・`range.start.column`・`range.end.line`（0 始まり）、`text`、`metadata.principle`。`compiled.rules` にない ruleId は捨てる。
- 除外：`profile.exclude_paths` か、そのルールの `excludePaths` に一致するパスは捨てる。`profile.overrides.paths` の glob に一致し、`disable` にその原則があれば捨てる。
- 例外コメント：該当行か、その直前の行に `wisdom-allow <ID>[, <ID>...]: 理由` があり、ID に原則が含まれていれば `waived`。理由がなければ例外にせず `invalidAllows` にも入れる。ID の正規表現は `[A-Z][A-Z0-9]*(?:-[A-Z0-9]+)*`。
- `diffBase`：ファイルごとに `git -C root diff -U0 --no-color <base> -- <rel>` の `@@ -a,b +c,d @@` から変更行の範囲（d=0 は削除だけなので無視、d 省略は 1）。git が追跡していないファイル（`git ls-files --error-unmatch` が失敗）は全行。git リポジトリでなければ絞り込まず、`errors` に「git リポジトリではないため差分での絞り込みをしませんでした」。範囲が [line, endLine] と重なる指摘だけ残す。
- 並び順：blocking → severity（error, warning, info, hint）→ file → line。
- `diffFingerprints`：指紋の出現回数で比べ、`before` より多く現れた分だけを「新しく入った指摘」として返す（多重集合の差）。

手順の文章（各3〜4行）：
- bugfix：再現条件を特定する ／ 修正前に失敗する再現テストを書く ／ 根本原因を直す（症状だけを隠さない）／ 同じ原因の箇所がほかにないか探す
- refactor：先に今の動作をテストで固定する ／ 振る舞いを変えない ／ 依頼と関係のない変更を混ぜない ／ 変更を小さく分ける
- new：先に構造と責務の分け方を決める ／ 選んだスタイルの原則に沿って実装する ／ 正常系と異常系のテストを書く ／ 設計判断を decisions.md に記録する
- feature：既存の設計・命名・書き方を確認して合わせる ／ 変更の影響範囲を調べる ／ 新しい振る舞いのテストを書く ／ 既存のテストが通ることを確かめる
- test：振る舞い（入力と結果）を確かめる ／ 境界値と異常系を含める ／ 時刻・乱数・通信に頼らない

## 6. `src/core/exporters.ts`（Claude Code 以外の環境向け）

- `exportAgentsMd(paths, compiled): string`：`<root>/AGENTS.md` の `<!-- ai-code-wisdom:begin -->` 〜 `<!-- ai-code-wisdom:end -->` の間を L0 の文章で置き換える（なければ末尾に追加、ファイルがなければ作る）。「進め方」の1行目は「ファイルを書いたら `wisdom check --changed` を実行し、[必須] の違反を直す」に置き換える。書いたパスを返す。
- `exportCursorRules(paths, compiled): string`：`.cursor/rules/ai-code-wisdom.mdc` に `---\ndescription: AI Code Wisdom の設計方針\nalwaysApply: true\n---\n` ＋ 同じ文章。
- `exportGitHook(paths): string`：`.git/hooks/pre-commit` に、`"{PLUGIN_ROOT}/bin/wisdom" check --project <ルート> --diff HEAD --fail-on blocking` を実行する sh を書き、実行権限を付ける。`<ルート>` は、設定がリポジトリのサブディレクトリにあっても届くように `"$(git rev-parse --show-toplevel)"/'<最上位からの相対パス>'`（最上位なら相対パスなし）と書く（リポジトリを移しても動くように相対で書く。リポジトリの外なら絶対パス）。`.wisdom` が既定の `<root>/.wisdom` 以外（`--wisdom-dir`）なら、同じ書き方で `--wisdom-dir` も付ける。検査が終了コード 2（設定が見つからないなど）で終わったときは、`wisdom export git-hook` のやり直しを標準エラーに案内する。既にあって自分が書いたもの（中身に `ai-code-wisdom` を含む）でなければ、上書きせずエラー。git リポジトリでなければエラー。

## 7. `src/hooks.ts`（Claude Code のフック）

```ts
export interface HookResult { stdout?: string; exitCode: number }
export function runHook(event: string, input: any, env: NodeJS.ProcessEnv): HookResult
```

共通：開始点は `env.CLAUDE_PROJECT_DIR ?? input.cwd ?? process.cwd()`、そこから `findProjectRoot`。見つからなければ何も出力せず 0（ただし `user-prompt-submit` だけは、下の「初回設定」を行う）。

**初回設定**（未設定のプロジェクトでの `user-prompt-submit`）：`takeFirstRunOffer(開始点, os.homedir())` が文字列を返したら、`hookEventName:"UserPromptSubmit"` の additionalContext で出す。
- 対象（`looksLikeCodeProject`）：git の作業ツリー、または直下に `package.json`・`tsconfig.json`・`pyproject.toml`・`setup.py`・`requirements.txt` のどれかがある、または直下か1つ下のディレクトリ（`.` で始まるもの・`node_modules`・`dist`・`build`・`venv`・`__pycache__` を除く）に対応言語のファイルがあるフォルダ。ホームディレクトリそのものとファイルシステムのルートは除く。
- 一度だけ：`~/.ai-code-wisdom/first-run.json`（`{"projects": {"<実パス>": "<ISO 時刻>"}}`）に記録があれば出さない。なければ**案内を出す前に**記録する（断られても、別のセッションでも、二度と聞かない）。記録が読めない・壊れているときは空として扱い、書き直す。プロジェクトの中には何も書かない。
- 文面：「[AI Code Wisdom] このプロジェクトは、まだ設計スタイルが設定されていません。このプロジェクトで聞くのは今回だけです。」に続けて、依頼の前に Skill ツールで `ai-code-wisdom:init` を呼び、主スタイルの質問に「今は設定しない」を加えること、選ばれたら設定せず `/ai-code-wisdom:init` を案内すること、済んだら元の依頼を進め、変更は `/ai-code-wisdom:style` でできること。
- 設定したあとは出さない（設定の変更は利用者が `/ai-code-wisdom:style` か `/ai-code-wisdom:init` を開いたときだけ）。出力する JSON は `JSON.stringify` した1行。セッション ID は `input.session_id ?? "unknown"`。

| イベント | 動作 |
|---|---|
| `session-start` | `cleanupOldSessions`。`renderSessionContext` に、`compiled.warnings` と `checkLock` の問題（`lock.json` が壊れていて読めない場合も含む）があれば「注意：…」として足し、`{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":…}}`。設定を読めないときは、L0 の代わりに「設定を読めないため、このセッションでは自動検査が止まっています。」・「理由：…」・`wisdom status` の案内を同じ形で返す |
| `user-prompt-submit` | `input.prompt` を `classifyPrompt`・`riskyPrinciples` にかけ、`renderTaskContext` が null でなければ `hookEventName:"UserPromptSubmit"` で additionalContext |
| `pre-tool-use` | 対象は `tool_name` が Edit / Write / MultiEdit で、`tool_input.file_path` がプロジェクト内・対応言語・`profile.exclude_paths` 外。ファイルがあれば検査して指紋を `lastBaseline` に（状態が新規なら `firstBaseline` にも、`existedAtStart=true`）。なければ新規状態は `existedAtStart=false`・両方空。`contextShown` が false なら `renderFileContext` を出し true にする。出すものがあれば `hookEventName:"PreToolUse"` で additionalContext だけ（permissionDecision は付けない） |
| `post-tool-use` | 同じ対象。検査して、状態があれば `diffFingerprints(state.lastBaseline, after)`、なければ（直前のフックが動かなかった場合）書き込んだ文字列（`content`／`new_string`／`edits[].new_string`）に snippet が含まれる指摘だけを新規とみなす。`changedLines` に書き込んだ文字列の行数を足す。blocking な新規指摘は `blockedCounts[指紋]` を 1 増やし、3 を超えたものは止めずに advisory 側へ移し「同じ違反を3回止めたため、以後は止めません。直せない理由をユーザーに説明するか、wisdom-allow を書いてください」を添える。`lastBaseline` を検査後の指紋に更新して保存。ledger に `{event:"edit", session, file, new:[{principle, ruleId, line, blocking}], after: 件数}`。blocking があれば `{"decision":"block","reason": blocking 文 ＋（あれば）advisory 文}`、なければ advisory を `hookEventName:"PostToolUse"` の additionalContext で。どちらもなければ出力なし |
| `stop` | `input.stop_hook_active` が true なら何もしない。セッションの状態がなければ何もしない。触ったファイル（存在するもの）をまとめて検査し、`diffFingerprints(firstBaseline, after)` のうち blocking で、`blockedCounts` が 3 を超えていないものが残っていれば `{"decision":"block","reason":"[AI Code Wisdom] 終了する前に、この作業で入った必須原則の違反を直してください：\n- {file}:L{line} [{ID}] {message}"}`。残っていなければ、レビューの判定：`profile.review` が always、または auto で `changedLines` の合計が 120 以上、かつ `meta.reviewRequested` が false なら、true にして保存し `{"decision":"block","reason":"[AI Code Wisdom] この作業では {N} 行を変更しました。終了する前に Agent ツールで subagent_type \"ai-code-wisdom:wisdom-reviewer\" を呼んでレビューを受け、必要な修正をしてから、最後に「適用した原則／検査の結果／未解決」を報告してください。"}`。どちらでもなければ ledger に `{event:"stop", session, files, changedLines}` を書いて出力なし |

## 8. `src/mcp.ts`（MCP サーバー）

`runMcpServer(): void` — 標準入出力で、1行1メッセージの JSON-RPC 2.0。SDK は使わない。

- `initialize` → `{ protocolVersion: params.protocolVersion ?? "2025-06-18", capabilities: { tools: {} }, serverInfo: { name: "ai-code-wisdom", version: TOOL_VERSION } }`
- `ping` → `{}`。id のない通知は無視。未知のメソッドは `{ code: -32601, message: "Method not found" }`。JSON として読めない行は `{ code: -32700 }`（id は null）。
- `tools/list` → 下の5つ（`inputSchema` は JSON Schema）。`tools/call` → `{ content: [{ type: "text", text }] }`、失敗は `isError: true` で文章を返す。

| ツール | 引数 | 結果 |
|---|---|---|
| `wisdom_principles` | `project_dir?`, `path?` | path があれば `renderFileContext`（null なら該当なし）＋ L0、なければ L0 |
| `wisdom_check` | `project_dir?`, `paths?: string[]`, `diff_base?` | `renderCheckReport` |
| `wisdom_explain` | `project_dir?`, `id` | 有効な原則 → なければプロジェクトのパック → なければ同梱パックから探して `renderExplain` |
| `wisdom_record_decision` | `project_dir?`, `decision`, `principle_ids?: string[]` | `decisions.md` に `- {YYYY-MM-DD}：{decision}（{ID, …}）` を追記 |
| `wisdom_styles` | なし | 同梱パックの `renderStyles` |

プロジェクトは `project_dir ?? env.CLAUDE_PROJECT_DIR ?? process.cwd()` から `findProjectRoot`。未設定なら「このプロジェクトは未設定です。/ai-code-wisdom:init で設計スタイルを選べます」（styles と explain の同梱パック検索は未設定でも動く）。

## 9. `src/cli.ts`（コマンド `wisdom`）

共通オプション：`--project <dir>`（既定は cwd。init 以外は `findProjectRoot` で上へたどる。見つからなければ「未設定です。wisdom init を実行してください」でエラー）、`--wisdom-dir <dir>`（設定の置き場所を変える。評価で使う。指定時は `--project` のディレクトリをそのままルートにする）。エラーは stderr に `wisdom: エラー：{message}`、終了コード 2。

| コマンド | 動作 |
|---|---|

| `styles [--json]` | 同梱パックの一覧 |
| `style` / `style set [--primary] [--secondary ...\|none] [--phase] [--review]` | 今の設定の表示／変更（`setStyle`） |
| `status` | 設定、パック（版・ハッシュ）、lock の確認、原則とルールの数、warnings、skipped |
| `principles [--json]` | 有効な原則を rank 順に `[{ID}] {levelLabel} {summary}` |
| `explain <ID>` | `renderExplain` |

| `audit [--json]` | 全体を検査し、原則ごとの件数（severity 別）、例外の一覧（`file:line [ID] 理由`）、理由のない例外、前回からの増減を表示。`audit-history.jsonl` に `{ts, total, byPrinciple}` を追記 |
| `update [--yes]` | `planUpdate` の差分（追加／削除／変更、ルールの変更有無）を表示。`--yes` で `applyUpdate` |
| `lock` | `relock` |
| `export agents-md\|cursor\|git-hook` | 6章 |
| `review-context [--diff <ref>]` | レビュー役のための材料。git なら `git diff --name-only <ref, 既定 HEAD>` と未追跡ファイル、git でなければ最新のセッションの状態にあるファイル。対応言語のファイルごとに：層、`renderFileContext`（無ければ必須原則の review）、そのファイルの静的検査の結果。最後に `git diff <ref> -- <files>`（400 行で打ち切り） |
| `hook <event>` | 標準入力の JSON を読み `runHook`。stdout を出して終了コードで終わる |
| `mcp` | `runMcpServer` |
| `help`・引数なし | 使い方（日本語） |

`bin/wisdom`：POSIX sh。シンボリックリンク経由でも自分の場所を解決し、`exec node "$DIR/../src/cli.ts" "$@"`。実行権限を付ける。

## 12. 評価の仕組み（`eval/`）

目的：同じ依頼を「プラグインなし（baseline）」と「あり（wisdom）」の Claude に実行させ、原則の違反・テストの通過・トークンを比べる。

```
eval/
  run.ts                    # 実行と集計
  tasks/<id>/task.yaml      # id, title, language, profile {primary, secondary[]}, steps[] (依頼文), test {functional, robustness}
  tasks/<id>/repo/          # 最初のプロジェクト（見えるテストを含む）
  tasks/<id>/hidden/functional/   # 依頼どおりに動くかの隠しテスト
  tasks/<id>/hidden/robustness/   # 原則が守られていれば通る隠しテスト（依頼文には書いていない堅牢さ）
  tasks/<id>/reference/     # 模範解答（隠しテストが正しいかを確かめるため。--dry-run で使う）
  results/<日時>/           # 結果（results.json, summary.md, runs/…）
```

`node eval/run.ts [--tasks a,b] [--conditions baseline,wisdom] [--reps 1] [--model sonnet] [--concurrency 3] [--out <dir>] [--dry-run]`

1回の実行（課題 × 条件 × 回）：
1. `repo/` を `<out>/runs/<task>__<cond>__<rep>/work/` に複製し、`git init`・commit（作者は環境変数で `eval`）。wisdom 条件では `node <ルート>/src/cli.ts init --project <work> --primary … --secondary …` をしてから commit。この commit を基準にする。
2. 各ステップで `claude -p "<依頼>" --output-format json --model <model> --permission-mode acceptEdits --setting-sources project --allowedTools <一覧>`（wisdom 条件は `--plugin-dir <ルート>` を足す）を、cwd を work にして実行（1ステップ最大 15 分）。ステップごとに新しいセッション。標準出力の JSON を `step-<n>.json` に保存し、`usage`（input_tokens, output_tokens, cache_creation_input_tokens, cache_read_input_tokens）、`total_cost_usd`、`duration_ms`、`num_turns`、`is_error` を集める。許可するツール：`Read Edit Write Glob Grep Agent "Bash(node --test:*)" "Bash(node:*)" "Bash(python3 -m unittest:*)" "Bash(python3:*)" "Bash(ls:*)" "Bash(git status:*)" "Bash(git diff:*)"`、wisdom 条件は `"Bash(wisdom:*)"` も。
3. 測定（隠しテストを置く前に）：課題の profile で `node <ルート>/src/cli.ts init --project <work> --wisdom-dir <run>/measure --primary … --secondary …`、続けて `check --project <work> --wisdom-dir <run>/measure --diff <基準 commit> --json --fail-on never`。指摘を severity 別・blocking・原則別に数える。重み付きの点数＝ error 3、warning 2、info 1。
4. 隠しテストを `<work>/hidden_tests/` に複製して実行。TypeScript は `node --test hidden_tests/<種類>/`（出力の `# pass N` と `# fail N`）、Python は `python3 -m unittest discover -s hidden_tests/<種類> -t .`（`Ran N tests` と `FAILED (failures=a, errors=b)` か `OK`）。
5. wisdom 条件では `.wisdom/ledger.jsonl` の行数も記録する（フックが実際に動いたことの確認）。

`--dry-run`：claude を呼ばず、`reference/` を work に上書きして 3〜4 を行う。隠しテストがすべて通ることを確かめるために使う。

集計：`results.json`（実行ごと）と `summary.md`（課題ごとに baseline と wisdom を並べた表：機能テストの通過率、堅牢さテストの通過率、必須違反の数、重み付き違反点、トークン合計、費用、時間、ターン数。最後に全体：違反点の減少率、機能テストの通過率の差、費用とトークンの増加率、完了条件「違反点が半分以下・機能テストの通過率が下がらない・費用の増加 20% 以内」の判定）。

課題は6つ（依頼文は日本語、API の形を明示する）：
